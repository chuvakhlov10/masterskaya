# Аварийный шлюз Мастерской

Статус: резервный код размещен на `https://masterskaya-six.vercel.app`;
действующие ключи сохранены только в Production. Адреса прописаны в
`src/reserve-gateway-config.js`, но `enabled: false` оставляет автоматическое
переключение выключенным до проверки с подключенным устройством. В «Система»
доступна кнопка «Проверить резерв»: она проверяет обе серверные функции с текущей
сессией и читает `status.json` через резерв. Неавторизованный health-ответ не
считается подтверждением готовности. Офлайн-режим сохраняется.

Шлюз использует существующий GitHub App, общий приватный репозиторий
`chuvakhlov10/masterskaya-data` и тот же реестр устройств. Отдельную базу данных
создавать не нужно. Проверка устройства для Ably выполняется внутри резервного
сервера и не обращается к Яндексу. GitHub, Ably и интернет на устройстве остаются
необходимыми для сетевой синхронизации; без интернета работает локальная очередь.

## Размещение на независимом сервере

Нужен Node.js 22 или новее и HTTPS перед сервером. Можно запустить непосредственно
`node server/start-reserve.js` (порт из `PORT`, по умолчанию 3000), либо собрать
контейнер из корня репозитория:

```sh
docker build -f server/Dockerfile -t masterskaya-reserve .
docker run --rm --env-file /secure/masterskaya-reserve.env -p 3000:3000 masterskaya-reserve
```

Секретный env-файл хранится вне репозитория. На управляемом хостинге задайте эти
значения через защищенные настройки окружения. Не передавайте их в чат, исходный
код, публичные адреса или переменные `VITE_*`.

Скопируйте **действующие значения** из конфигурации основных функций Яндекса:

| Переменная | Назначение |
| --- | --- |
| `GITHUB_APP_ID` | Существующий GitHub App с доступом к репозиторию данных |
| `GITHUB_APP_PRIVATE_KEY_B64` | Его существующий закрытый ключ в base64 |
| `MASTERSKAYA_SESSION_SECRET` | Тот же ключ подписи сессий, иначе текущие устройства не войдут |
| `MASTERSKAYA_SESSION_VERSION` | Та же версия сессий, без изменения |
| `ABLY_API_KEY` | Действующий ключ Ably для живых обновлений |
| `MASTERSKAYA_MIN_STORAGE_PROTOCOL` | Тот же минимальный протокол, если установлен на основном сервере |
| `MASTERSKAYA_STOCK_EPOCH` | Та же эпоха склада, если установлена на основном сервере |

Не генерируйте новый ключ сессий и не меняйте настройки основного сервера.
Необязательные `MASTERSKAYA_RESERVE_PROVIDER`, `MASTERSKAYA_BUILD_ID` и
`MASTERSKAYA_BUILD_DATE` позволяют различать резерв в диагностике. Если хостинг
обрабатывает файлы `api/*.js` как Node.js-функции, доступны готовые адаптеры
`api/storage.js` и `api/ably.js`; у такого размещения необходимо проверить
лимиты времени и размера запросов на выбранном тарифе.

## Проверка перед включением

1. Через HTTPS запросить `POST /api/storage` и `POST /api/ably` с телом
   `{"action":"health"}` и заголовком
   `Origin: https://chuvakhlov10.github.io`. Убедиться, что конфигурация ключей
   отражается как `configured`. Сам по себе ответ без сессии не проверяет доступ
   к данным.
2. Повторить health-запросы с `X-Masterskaya-Session` действующего устройства.
   Получить `authenticated: true`, `deviceRegistry: ok` на обоих маршрутах и
   `githubApp: ok` на storage. Сессию использовать локально, не сохранять в
   истории shell и не публиковать в логах.
3. Проверить CORS preflight `OPTIONS` с заголовками `Content-Type` и
   `X-Masterskaya-Session` с основного сайта. Затем выполнить авторизованный GET
   `status.json` на ветке `data-backups` через storage и получить токен Ably.
4. Только после этих проверок установить `enabled: true` в
   `src/reserve-gateway-config.js`, собрать и выпустить клиент. Адреса оставлять
   постоянными, не использовать защищенный preview-домен.
5. На проверочном устройстве заблокировать оба адреса функций Яндекса в DevTools,
   открыть последнюю синхронизированную версию, записать тестовую операцию и
   проверить ее на втором устройстве. Проверить в диагностике маршрут «Резерв»,
   затем снять блокировку и убедиться в возврате к основному серверу и отсутствии
   дублирования операции.

Клиент переключает безопасные запросы при сетевых ошибках, таймаутах и временных
HTTP-ошибках. При настроенном резерве ожидание основного шлюза ограничено 6
секундами. После отказа следующие запросы идут на резерв, спустя минуту клиент
снова пробует основной. Запись повторяет исходное тело вместе с SHA; конфликт
409 передается существующей логике чтения и объединения, чтобы повторный запрос
не перезаписал новые данные. Ошибки авторизации и одноразовые операции
подключения/восстановления автоматически на второй сервер не повторяются.

Откат: установить `enabled: false` в `src/reserve-gateway-config.js`, собрать и выпустить
клиент. Сессии, остатки и локальные очереди при этом сохраняются.

Проверки: `npm run check`, включая тесты `gateway-failover.test.mjs` и
`reserve-node-gateway.test.mjs`. Боевой резерв считается включенным только после
успешной проверки с настоящими ключами и выпуском настроенных адресов.
